# Lamlet Render Lab library: render_lab (design draft)

Lamlet and its [`std` library](../../../../lamlet/plans/lamlet-stl.md) are general purpose. All Render Lab-specific script features
belong to the existing `packages/render_lab/` package in the Render Lab checkout. This document describes that extension, not a new language kernel
or a runtime implementation. The [integration plan](lamlet-integration.md) covers migration and validation.

## Boundary

| Layer | Owns |
|---|---|
| Independent language/core and `std` | Dollar-region scanning and ignored-text spans, syntax, lexical bindings, lambdas, types, arithmetic, lists, records, strings, modules, bytecode, static evaluation, `[Assert a b]`, typed native stubs and host registration. |
| `render_lab` script modules | Rich text/document values, presentation of retained prose and evaluated regions, formula/code/color constructors, narration projections/anchors, timeline and animation descriptions, viewer/scene adapters. |
| Native functions owned by `render_lab` | Formula layout/rendering adapters, typed access to the lab's value/action/image registries, explicit frame/event context, and scheduling/resource integration. |
| Investigation packages | Feature-specific values, actions, shaders, datasets, and demonstrations exposed through generic interfaces. |

The core can run without any of the lower layers. It knows no scene keys, frame counters, TTS rules, language
editions, text-table keys, GPU objects, package manifests, or renderer types. A host may register other capabilities,
including IO, without importing Render Lab. Core errors are generic source diagnostics; `render_lab` decides how to show
them in the viewer or video builder.

This is a design change to the language boundary. Existing renderer/native implementations are not being moved or
refactored during this documentation task. When implementation begins, script exports and their native adapters
live under `render_lab`; the lab supplies only generic facilities needed by multiple consumers.

## Package and module layout

Proposed source layout (names are not created by this plan):

```text
packages/render_lab/
  language/
    text.*          document items, rich text, content adapters
    formula.*       formula/code-span values and speech alternatives
    timeline.*      animation descriptions, anchors, sequencing
    viewer.*        scene values, actions, images, event adapters
    story.*         .story presentation/profile and preparation operations
  src/script/       native host bindings, compiled with render_lab's existing lab::utility code
  build/language/   generated bytecode/artifacts, ignored
```

The eventual source extension is a language decision. Modules are declared resources in `render_lab` collections and
exported through the existing manifest import/export rules. For example, a resource `script/text` could map to
language module `render_lab.text`; its full resource key would be `render_lab.script/text`. Resource keys, module names, and
text-table keys are separate identifiers. The general compiler uses a resolver interface; the lab's adapter
enforces package imports/exports and resolves built resources through `lab::resources`.

The [language package system](../../../../lamlet/plans/lamlet-packages.md) imports `render_lab` with `[Import render_lab]`, `[Import* render_lab]`, or
`[ImportAs render_lab rl]`. Its proposed public root interface re-exports constructors/types such as `colored`, `rgb`,
and `ColoredString` from the internal modules, making `render_lab.colored` or `rl.colored` available. It may also export
submodule namespaces such as `render_lab.text`. Lab manifest visibility controls access to module resources; the
language export table controls access to symbols. Both checks apply, and importing an implementation resource
does not expose its private bindings. Example consumer code:

```text
$[ImportAs render_lab rl]
${rl.colored "Hello" {rl.rgb 255 128 0}}
```

Generated modules stay in their package's ignored `build/` and are declared as built resources if shipped through
the loader. A generic compilation processor can be added if justified; do not bake a story-only processor into
the language. Keep resources lazy, loaded when their module/scene is needed. `render_lab` currently has no separate
cdylib: its `src/` is compiled into the lab as `lab::utility`; this plan does not assume a new library/negotiation
entry. The independent language crate cannot depend on that code or on the lab's package loader.

## Source notation and primitive boundary

Use the general STL's `{^ {...} ...}` lambdas, primitive immutable values, explicit static/runtime capabilities,
exact arity, and proposed `K.variadic` bridge. An `R.*` operation below is supplied by `render_lab`'s native adapter, never by
the language kernel. It is explicitly registered with a signature and stage requirements. Qualified names such
as `render_lab.colored` require `[Import render_lab]`; the alias form above uses `rl.colored`. Implementation blocks below
refer directly to their own package definitions and their configured `std` dependencies.

`render_lab` may provide ordinary aliases to general `std` functions, but there is only one implementation of their
semantics. Type-producing constructors remain ordinary `Struct`, `Field`, and `Nominal` operations. Presentation
is not inferred from field names.

## Presentation types and constructors

Canonical types are exported under qualified nominal tags such as `render_lab.Color` and `render_lab.ColoredString`. Aliases
preserve identity. Structural records that happen to have the same fields do not gain presentation behavior.

| Type | Representation/meaning |
|---|---|
| `Color` | Unpremultiplied sRGB `r,g,b,a`, finite Float components in `[0,1]`. |
| `ColoredString` | Exactly `string:String`, `color:Color`. |
| `Formula` | `latex:String`, `spoken:String`, `display:Bool`, `colors:List Color`. |
| `CodeSpan` | `code:String`, `spoken:String`. |
| `Content` | Ordered immutable document items; no embedded evaluator or mutable scope. |
| `AnimationTrigger` | Immutable scheduling description, including nested sequence/parallel groups. |

The first four use nominal wrappers over structural records. Content and recursive animation descriptions can be
registered immutable host datatypes with checked constructors; their representations do not add primitive cases
to the general language. A generic host-type interface must support their validated handles without exposing
addresses or borrowing. Generic equality is unavailable unless an adapter registers a lawful value equality.

Source type definitions use the general STL rather than special rendering-language syntax:

```text
$[# ColorData [% {Struct
    {Field "r" Float} {Field "g" Float} {Field "b" Float} {Field "a" Float}
}]]
$[# Color [% {Nominal "render_lab.Color" ColorData}]]
$[# ColoredStringData [% {Struct {Field "string" String} {Field "color" Color}}]]
$[# ColoredString [% {Nominal "render_lab.ColoredString" ColoredStringData}]]
$[# FormulaData [% {Struct
    {Field "latex" String} {Field "spoken" String}
    {Field "display" Bool} {Field "colors" {List Color}}
}]]
$[# Formula [% {Nominal "render_lab.Formula" FormulaData}]]
$[# CodeSpanData [% {Struct {Field "code" String} {Field "spoken" String}}]]
$[# CodeSpan [% {Nominal "render_lab.CodeSpan" CodeSpanData}]]
```

The ordinary constructors then use `Record`, `Member`, and `wrap`:

```text
$[# rgba {^ {r g b a}
    {if {and {<= 0.0 r 1.0} {<= 0.0 g 1.0} {<= 0.0 b 1.0} {<= 0.0 a 1.0}}
        {wrap Color {Record ColorData
            {Member "r" r} {Member "g" g} {Member "b" b} {Member "a" a}
        }}
        {error "color component outside [0,1]"}
    }
}]
$[# rgb {^ {r g b}
    {if {and {<= 0 r 255} {<= 0 g 255} {<= 0 b 255}}
        {rgba {/ {float r} 255.0} {/ {float g} 255.0} {/ {float b} 255.0} 1.0}
        {error "color byte outside [0,255]"}
    }
}]
$[# colored {^ {text color}
    {wrap ColoredString {Record ColoredStringData
        {Member "string" text} {Member "color" color}
    }}
}]
$[# formula {^ {latex spoken}
    {wrap Formula {Record FormulaData
        {Member "latex" latex} {Member "spoken" spoken}
        {Member "display" false} {Member "colors" K.nil}
    }}
}]
$[# displayFormula {^ {latex spoken}
    {wrap Formula {Record FormulaData
        {Member "latex" latex} {Member "spoken" spoken}
        {Member "display" true} {Member "colors" K.nil}
    }}
}]
$[# codeSpan {^ {code spoken}
    {wrap CodeSpan {Record CodeSpanData {Member "code" code} {Member "spoken" spoken}}}
}]
$[# toItems {^ {value} {R.toItems value}}]
$[# content {K.variadic 0 0 {^ {items}
    {R.content {flatten {K.mapArgs items toItems}}}
}}]
```

`rgba` accepts four Floats; `rgb` accepts three Int bytes in `[0,255]`. Invalid components error. `colored`,
`formula`, `displayFormula`, and `codeSpan` each take two arguments as shown. Expected Record field types resolve
the empty color lists as `List Color`. `content` is variadic and may accept different registered presentation types.
`K.mapArgs` specializes the constrained `toItems` adapter for each static argument type. `R.content` validates the
flattened item list and wraps it as the immutable host Content datatype; those two `R.*` operations remain native.

`toItems` is the explicit `render_lab` conversion:

- String or scalar with a `std.str` representation becomes one Text item.
- ColoredString, Formula, and CodeSpan become their corresponding styled/formula/code items.
- Unit contributes no items; Content contributes its existing items in order.
- AnimationTrigger contributes a scheduler item, without executing it.
- Other values require a registered pure adapter or produce a presentation error. Ordinary lists do not
  automatically become heterogeneous document content; convert them explicitly.

`str` and `format` stay in the general STL. `render_lab` supplies separate spoken/caption/export projections. Strings
returned by programs are data and are never reparsed as code. Formula alternatives are explicit and retain the
lab's existing formula layout limits. Rendering consumes prepared items; measuring or painting does not execute
scripts, schedule effects, or register handlers again.

## Text and story reader

All Lamlet documents follow the core [source convention](../../../../lamlet/plans/lamlet-source.md): only `$name`, `${...}`, and `$[...]`
regions are active; everything else is a comment to the evaluator. `render_lab` preserves those ignored spans as prose
and converts active expression results to Content at their source positions. `$$` displays one literal dollar.
Bare braces/brackets remain prose and do not execute definitions, imports, or static evaluation.

`$[# ...]`, `$[% ...]`, `$[Import ...]`, and other prefixed meta forms retain their core meanings. Declarations
produce no document items. Nested forms inside an active region need no further dollar. Qualified lookup uses
`$rl.label` for an exported value or `${rl.colored "Hello" {rl.rgb 255 128 0}}` for a call after the matching import.
The core owns recognition/escaping even inside Markdown fences and multiline forms. The profile adds story
structure and presentation rather than another dollar grammar or a bare-bracket execution path.

Definitions and the collected content are separate. A declaration applies to subsequent uses in the enclosing
document body, including later paragraphs; a nested function has its own scope. The reader does not encode the
binding environment in a displayed content list. There is no special suffix `{* ...}` operator; `*` is arithmetic.

`.story` headings, beats, sentence boundaries, source citations, narration alternatives, and translation alignment
belong to this profile. They are not new core AST or VM instruction kinds. A frontend can elaborate them into
ordinary language/module operations plus `render_lab` data and host calls.

Static preparation extracts the exact spoken text before TTS, including static formula alternatives and formatted
values. Runtime dependencies cannot enter that output. Stable sentence/cue IDs link prepared content to measured
word timestamps; timing resolution runs after speech synthesis. Preserve the current English narration/shared
timing policy for the zh-CN edition, with translated captions and one corresponding sentence per English sentence.
Those are policies of this package, not definitions of the general language's static stage or String type.

## Animation and timeline descriptions

Pure constructors, with exact fixed-prefix/variadic packing signatures:

```text
$[# setValue {^ {key value} {R.setValue key value}}]
$[# animate {^ {key from to seconds} {R.animate key from to seconds}}]
$[# sequence {K.variadic 0 0 {^ {triggers} {R.sequence triggers}}}]
$[# parallel {K.variadic 0 0 {^ {triggers} {R.parallel triggers}}}]
$[# clamp01 {^ {u} {if {< u 0.0} 0.0 {if {> u 1.0} 1.0 u}}}]
$[# linear {^ {u} {clamp01 u}}]
$[# smoothstep {^ {u}
    [# t {clamp01 u}]
    {* t t {- 3.0 {* 2.0 t}}}
}]
```

`setValue` takes a static registered key and a value of its declared type. `animate` takes four arguments: a static
String key whose registry type is Float, two Float endpoints, and nonnegative Float seconds. Sequence/parallel are variadic AnimationTrigger operations,
with the entire tail packed into one list for their equations. Sequence offsets starts by prior child durations;
parallel starts children together and has maximum duration. Empty groups have duration zero. Reject overlapping
writers to a single key. Descriptor construction does not immediately update a scene.

For an animation anchored at `t0`, seek-independent evaluation is:

```text
$[# valueAt {^ {base from to seconds t0 t}
    {if {< t t0}
        base
        {if {= seconds 0.0}
            to
            {+ from {* {- to from} {linear {/ {- t t0} seconds}}}}
        }
    }
}]
```

This helper accepts Float inputs and a validated nonnegative duration. `R.setValue`, `R.animate`, `R.sequence`,
and `R.parallel` implement the checked host datatype constructors and scheduling contracts described here. Their
wrappers do not execute updates. The endpoint holds after completion. Narration timing selects anchors; paint/layout does not. `render_lab` checks
unknown keys/types, action arguments, image kinds, and handler schemas through the lab's registries. Function
signatures/stage constraints come from host metadata. Investigation-specific algorithms stay in their packages.

Persistent simulations require explicit state/event replay or checkpoints. They are a later `render_lab` extension,
not hidden mutable state added to core lambdas or content values.

## Viewer and resource capabilities

Source wrappers for two Runtime-only adapters are:

```text
$[# time {^ {} {R.timelineSeconds}}]
$[# value {^ {key} {R.readRegisteredValue key}}]
```

`{render_lab.time}` has zero source arguments; `{render_lab.value "key"}` has one. The native adapter receives explicit C from the
host interface. These functions require Runtime and declare their result types; key schemas are known statically.
They do not expose a process wall clock. A script closure can be created statically while retaining a latent
Runtime requirement; calling it statically fails generic stage checking.

Image/resource constructors, picking, and action calls follow the same registration mechanism. Resources resolve
through full package keys and imports/exports, with lazy loading. TTS, FFmpeg, and GPU adapters may have effects
through explicit host capabilities. The core compiler neither discovers these tools nor runs them during checking.

Use the [native stub interface](../../../../lamlet/plans/lamlet-native.md) to expose concrete host APIs. For example, a package can bind a
Runtime-only timeline read without placing a timeline primitive in the general language:

```text
$[Import* std]
$[Native timelineSeconds [% {| Float}] "render_lab.viewer/time" Runtime]
$[# time {^ {} {timelineSeconds}}]
```

The native implementation receives the explicit viewer context through the registry callback. Type/key-dependent
viewer APIs need generated concrete declarations or typed adapters over supported values; the first Native stub
ABI does not silently acquire arbitrary dependent/generic foreign signatures. Opaque Content/AnimationTrigger
adapters follow the registered native type and lifetime contracts.

## Implementation and validation

1. Build and test the standalone language/STL first, without loading `render_lab`, the lab, packages, or GPU libraries.
2. Add the generic host/module interfaces, then implement/register these capabilities from `render_lab` modules and
   `packages/render_lab/src/` native adapters. Keep package version/import/export checks in the lab adapter.
3. Have `tools/video` call the one compiler/scanner with the `render_lab` presentation profile/resolver. Keep Python as orchestration rather
   than another implementation of language semantics. Story-specific commands can be package-defined or lab CLI
   adapter commands; the general compiler remains usable independently.
4. Check static TTS inputs, cue resolution, both text editions, formula limits, and unchanged presentation against
   recorded baselines. Verify live value reads, picks, animation conflicts, and standalone seeked frames.
5. Run package/build tests required by Render Lab's AGENTS.md when implementation changes code/resources. Use offscreen visuals
   and one GPU job at a time. Core semantic tests remain GPU/TTS-free.

No package manifests, resource collections, native bindings, or interpreter implementation are created by this
design document. Package-author export declarations, profile selection, and the generic host datatype ABI remain Phase 0
decisions; their location and independence requirements are fixed by the boundary above.
