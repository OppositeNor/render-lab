# Architecture and code map

[Render Lab](../README.md) · [Build](../BUILD.md) · [简体中文](architecture.zh-CN.md)

## Application and interface

| Path | Role |
|---|---|
| [`src/main.rs`](../src/main.rs), [`lab/`](../lab/Cargo.toml), [`lab/src/cli.rs`](../lab/src/cli.rs) | The binary, which only runs the lab: a Rust dylib that the binary and every package's library link, so they share one lab (its code and its state). The command line is the lab's. |
| [`lab/src/home/`](../lab/src/home/), [`lab/src/frost.rs`](../lab/src/frost.rs), [`packages/render_lab/shaders/frost.wgsl`](../packages/render_lab/shaders/frost.wgsl) | The homepage: the title, Config, and selection pages, over the title investigation's backdrop scene (`investigations::title`, O3DE's lighting for now; the loading page until it has loaded, `home --snapshot --page starting`), halved twice, blurred, tinted, and grained. |
| [`lab/src/config.rs`](../lab/src/config.rs), [`lab/src/volume.rs`](../lab/src/volume.rs) | The settings file: its location, reading it (with `toml_edit`), and writing it; a sound's volume (a level and a mute switch) and its slider, on the Config page and in the viewer's dock. |
| [`lab/src/theme.rs`](../lab/src/theme.rs), [`lab/src/palette.rs`](../lab/src/palette.rs), [`themes/`](../themes) | Themes: finding and reading the theme files (the build copies `themes/` beside the binary), and the interface's colours in use (`palette::theme()`, `palette::text()`, ...), the lab's own until a theme is set; the overlays' colours stay constant. |
| [`lab/src/loading.rs`](../lab/src/loading.rs) | The loading step: nothing a scene needs is read at start-up. When the viewer opens (or the homepage shows its backdrop), a worker thread prepares the scene's resources, its statics, and its renderer while the window shows the progress; `home --snapshot --page loading` draws that page offscreen. |

## Scenes and rendering

| Path | Role |
|---|---|
| [`lab/src/text.rs`](../lab/src/text.rs), [`lab/src/readback.rs`](../lab/src/readback.rs), [`lab/src/gpu.rs`](../lab/src/gpu.rs) | Fonts and text, reading frames back and saving PNGs, and the GPU device. Text tables, pseudo-code listings, and source indexes are resources of each layer's package, read when first used (`i18n::Table`). |
| [`lab/src/formula.rs`](../lab/src/formula.rs), [`lab/src/rich_text.rs`](../lab/src/rich_text.rs), [`packages/render_lab/assets/mitex/`](../packages/render_lab/assets/mitex) | Formulas: LaTeX typeset by Typst (through MiTeX's scope) into coverage masks tinted when drawn, and text with formula tags laid out on one baseline. |
| [`lab/src/scene.rs`](../lab/src/scene.rs), [`packages/render_lab/scenes/`](../packages/render_lab/scenes/study-room.lam), [`lab/src/terrain.rs`](../lab/src/terrain.rs) | The lab's scenes, by `SceneId`: the study room, and hills of terrain under the sky. Each is a data file, the resource `scene/<key>` (its objects, shapes, materials, light, lighting constants, where a camera sees it from, and the terrain's heightfield), read when a scene is first built. Each demonstration shows one (`Investigation::demo_scene`, the study room by default); the renderer prepares a scene the first time a frame needs it and keeps it for switching back, and the viewer shows a tab per scene when an investigation's demonstrations use more than one, with the scene's demonstrations beside them. The terrain is a heightfield on a grid (`SHAPE_TERRAIN`), drawn as triangles and traced cell by cell on the GPU (`intersectTerrain`) and the CPU (`Terrain::intersect`); its heights are given samples or, opt-in, fractal Perlin noise with a fixed seed. |
| `lab/src/*.rs` (the rest) | The scene renderer, the deterministic recorder, the viewer and its dock, the timeline player and its animation (`animation.rs`: eases, paths, orbits, waves, and Play clips), the actions a story runs in a package's code (`actions.rs`, declared with `#[lab::actions]`), the GPU image kinds a package's shaders define and a story makes instances of (`views.rs`; a kind may read the package's pass-chain targets with `reads=`), the struct-panel records (`layout.rs`, `packages/render_lab/shaders/types.wgsl`), and the `Investigation` trait (`investigation.rs`). |

## Packages and runtime resources

| Path | Role |
|---|---|
| [`packages/render_lab/src/`](../packages/render_lab/src/mod.rs) | The standard package's code, built into the lab as `lab::utility`: what investigations share instead of each writing it, namely the picture inset and the images a story shows by key (`inset`), a selftest's report, still frames, and test inputs (`selftest`), a package's source index (`sources`), its text table (`text_table!`), and a demonstration's Play animation sampled (`demo`). |
| [`lab/src/feature/`](../lab/src/feature/mod.rs) | The viewer's features: each tab of the dock, and each panel with state of its own, is a `Feature` and the state it keeps per viewer and per recording (Parameters, Experiments, Code, Sources, Prerequisites, Frame graph, Quiz, Captions; Performance, without a tab), with its dock, panel, story panels, full-screen view, homepage button, and snapshot pages in its own module. The viewer and the recorder ask the registry for them and name none; a package's library may add its own (the `features` handle). |
| [`lab/src/investigations.rs`](../lab/src/investigations.rs), [`lab/src/plugin.rs`](../lab/src/plugin.rs) | The investigations come from the packages' libraries. A package with code names its `library` (a cdylib) and its `negotiate` symbol; the loader opens the library at run time and calls that function with a C structure (the loader's interface version, its lab's build, and a map), and the function, which `lab::negotiate!` writes, checks them against the lab it was compiled with and registers the package's method handles in the map by name (`investigations`, and optionally `features`), the way the Vulkan loader negotiates with a layer. A library built against another lab is refused, not called. |
| [`lab/src/packages.rs`](../lab/src/packages.rs), [`packages/`](../packages) | Packages: the lab's content comes in folders of `packages/`, each with a `manifest.toml` (name, author, contact, license, the packages it `import`s, the keys it `export`s, and what it `provides`: collections of resources, and demos, a narrated timeline and its audio). The lab scans them at start-up and orders them by their imports. A package names its own resources by key and another's as `<package>.<key>`, only of a package it imports and only what that package exports. [`render_lab`](../packages/render_lab/manifest.toml) holds what every investigation shares (the sky, the teapot, the scenes, fonts, the lab's WGSL and text); each investigation has its own (`Investigation::package`; [`o3de_lighting`](../packages/o3de_lighting/manifest.toml)). A package is self-contained: its manifest, content, code (`src/`, `Cargo.toml`), and what its tools write (`build/`: timelines, narration) are all in its folder, and it may come with its library built, in its `lib/`. `render-lab packages` lists them, with their libraries and handles. |
| [`lab/src/pipeline/`](../lab/src/pipeline/mod.rs), [`lab/src/resources.rs`](../lab/src/resources.rs) | Built packages: the loader reads only `packages/` beside the binary (`target/release/packages/<name>/`: each a manifest, its resources, and its library), by full key (`render_lab.teapot`). Run from a source checkout, the lab first builds the checkout's packages there ([`lab/src/cook.rs`](../lab/src/cook.rs)), incrementally: each resource is made by its kind (`file` and `directory`: linked; `radiance`: an HDRI made into the environment's levels; `mesh`: an OBJ made into a BVH) only when its source, parameters, or processor changed, so an edit shows on the next launch. A built package that did not come from the checkout is read as it is. `render-lab cook` runs the build and reports it; `render-lab resources` lists the resources. |
| [`lab/src/shaders.rs`](../lab/src/shaders.rs), [`packages/render_lab/shaders.toml`](../packages/render_lab/shaders.toml) | WGSL at run time: each `[[shader]]` a package declares is its `parts` in order (WGSL resources or other shaders; the lab's pass modules start with `render_lab.shader/prelude`), composed and validated by naga when the lab creates it, so an edited shader shows on the next launch and an error names its file and line. naga also lays out `wgsl/types` for the struct panel. |

## Values and demonstrations

| Path | Role |
|---|---|
| [`lab/src/values.rs`](../lab/src/values.rs), [`lab/src/shader_data.rs`](../lab/src/shader_data.rs), [`lab/derive/`](../lab/derive/src/lib.rs) | Values by key: what the dock, timelines, and stories set, each with its type, default, range, unit, labels, name, colour, and text. A Rust struct declares them with `#[derive(lab::Values)]` (the camera's, `camera.yaw`, `camera.x`, …; an investigation's, `packages/o3de_lighting/src/o3de/lighting/values.rs`); a shader declares the members of its uniform struct with `{@ key=… default=… range=…}` tags in `///` comments, which the lab reads with naga and packs into the buffer each frame (the investigation fills the members tagged `derived`). The declarations are the schema; a shot stores every value by key in its type (`ShotState::values`: `state["key"]`, `p`, `set`, `set_value`, a vector's components by their own keys), and converts them to and from a typed struct with serde (`view`, `store`). A timeline blends them by number, and a flag or an index snaps where its type does; a timeline may write a value as a number, `true`/`false`, a vector (`lightPosition=0.4,1.9,0.8`), or an option's name, which the lab resolves against the declaration when it loads (a story's cue writes the same through its vocabulary: `{lightPosition {' 0.4 1.9 0.8}}`, `viewModeNdotl`). A choice is a `#[derive(lab::Choice)]` enum whose variants are its options (`viewMode=ndotl`): a shader's tag names it (`choice=ViewMode`), the dock offers its options, and the lab writes its WGSL constants into the package's git-ignored `build/generated/` whenever it loads the investigation (a `built = true` resource the shader composes; the build's shader check takes it once it exists). `render-lab choices` lists them. A derived struct also reads and writes its fields by short key (`camera.set_field("yaw", 30.0)`). `Dock::values`, `Dock::value`, and `Dock::choice` draw from the declarations; `render-lab values [--label L]` lists them. |
| [`lab/src/demo.rs`](../lab/src/demo.rs) | Demonstrations as data: an investigation's package declares its parameters (a values struct, above, or `params.toml`), the order of its demonstrations, one file per demonstration (title, tab, hint, scene, listing, camera, and the parameters it changes, with shared presets), and the lab builds each demonstration's starting state from them. What a demonstration draws, its dock, and its Play animation stay the investigation's code (`packages/o3de_lighting/demos/` is the example). |
